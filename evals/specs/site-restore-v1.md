# 页面还原 E2E 评测方案

| 字段 | 内容 |
| --- | --- |
| 评测名称 / 版本 | UI Reverse Engineer Site Restore E2E / 1.0-draft |
| 状态 | 待产品负责人确认；下列阈值、样本规模与实验组是提案，不是已校准结论 |
| 评测目标 | 比较不同方案生成的页面还原效果，建立当前基线，并产出可定位到维度和 case 的优化建议 |
| 评测单元 | 一次固定输入、一次完整生成流程及其最终可运行的 `restored/` 网站项目；按 case 配对比较 |
| 范围 | 只评 `--restore` 指定页面、视口与交互状态的 E2E 还原质量；不评技能触发、brief 单独质量或其他三种模式 |
| 产出 | 每组的门槛结果、分维度得分、差值及区间、回归 case、错误归因、下一版目标 |

## 被测对象与比较设计

固定模型为 `gpt-6-luna`，reasoning effort 为 `high`。每个 case 使用相同参考输入、用户任务、视口和浏览器环境。建议先比较四组：

| 组 | Harness | 附加能力 |
| --- | --- | --- |
| A 基线 | 关闭 | 无 |
| B Harness | 开启 | 无 |
| C Product Design | 开启 | Product Design Plugin |
| D UI Reverse Engineer | 开启 | 当前版本 ui-reverse-engineer Skill |

这是“逐步增加方案”的比较，不能从 A-D 的总差值中单独识别 Plugin、Skill 与 Harness 的交互效应。若决策需要识别这些交互，应在后续版本扩成 Harness 开/关 × 能力（无 / Plugin / Skill）的 2×3 设计。运行前需确保四组都能在相同客户端环境下执行；若某组无法关闭 Harness 或注入指定能力，记录为不可比并停止该组因果归因，不用其他组代替。

## 评分维度与门槛

每项按 Rubrics 的 0–4 级评分，再按权重折算成 100 分。代码检查只负责确定性契约与硬门槛；视觉和语义由盲评评委评分；有争议或校准样本由人工裁决。维度分由评分规则固定合成，不以 LLM 自由总评替代。

| 维度 | Schema ID | 定义 | 权重 | 主评分方式 | 维度通过线 |
| --- | --- | --- | ---: | --- | ---: |
| 视觉结构与布局 | `layout` | 页面分区、层级、对齐、留白、尺寸、首屏构图与参考的相似度 | 25 | 盲评 LLM + 人工抽审；截图差异/几何检查作辅助证据 | ≥3/4 |
| 视觉样式与细节 | `style` | 色彩、字体、边框、阴影、图标、图片裁切及组件状态的匹配度 | 20 | 盲评 LLM + 人工抽审 | ≥3/4 |
| 内容与组件完整性 | `content` | 重要文案、区域、组件、信息层级是否覆盖；明确禁止臆造事实 | 15 | 参考清单规则 + 盲评判定 | ≥3/4，关键内容漏失触发红线 |
| 交互与状态 | `interaction` | 任务指定的按钮、标签、菜单、表单及可见状态是否可操作且反馈合理 | 20 | 浏览器自动化检查 + 盲评边界项 | ≥3/4；核心交互不可用触发红线 |
| 证据忠实度 | `fidelity` | 可见证据、输入明确要求和推测的区分；不把缺失信息编成确定事实 | 10 | 有标注的参考事实表 + 盲评 | ≥3/4；重大无依据事实触发红线 |
| 响应式与运行稳健性 | `robustness` | 目标视口下布局稳定、无溢出/遮挡/致命控制台错误，声明支持的窄视口可用 | 10 | 浏览器自动检查 + 盲评 | ≥3/4；页面无法加载触发红线 |

### 红线（硬门槛）

每个 case 使用同一组稳定红线 ID，以便跨 case 汇总；触发条件必须对照该 case 冻结的核心内容、交互、事实和视口判断。非该 case 范围内的条件标为 `not_applicable`，不能为了填表虚构失败。任一适用红线失败，该 case 标为失败；严重度和影响范围必须记录。组级门槛提案：S3 严重红线必须为 0；S2 重大红线失败率 ≤5%，并且不得集中在关键流程。若确认集只有 24 个 case，单次失败就超过 4%，因此 S2 门槛在该样本规模下也等价于零失败；最终容忍率需结合确认集规模校准。

红线由最终 UI 交付契约推导：先冻结页面状态/视口、关键区域与内容、必须完成的交互、可核实事实/未知项和允许的副作用；再对每条红线判断“什么缺陷会使这项明确要求不可见、不可理解、不可操作或改变其含义”。固定 ID 用于跨 case 汇总；每个 case 的 obligations、states、interaction steps、known/unknown facts 和副作用边界提供判定对象。Loop 的 finding 严重度 (`blocking`/`obvious`/`minor`) 属于迭代诊断，不能代替本节最终 E2E 严重度。

| 红线 ID | UI 触发条件 | 不触发的相邻问题 | 必需证据 / case 输入 |
| --- | --- | --- | --- |
| `runnable` | 契约要求的页面/状态无法经记录的启动路径打开、页面空白/崩溃，或关键状态不可到达 | 页面能加载但资源、字体或视觉细节有偏差；按对应质量维度记录 | 启动命令、required state 的加载结果、截图或运行诊断 |
| `structure` | 冻结为关键的区域缺失，或层级错乱导致页面核心用途无法辨认 | 区域存在但比例、留白、顺序有局部差异 | obligation、参考与候选同状态截图、受影响区域 |
| `interaction` | 冻结的核心动作不能完成，或完成后没有可观察的预期状态反馈 | 未冻结、参考也未证明的隐藏行为或推测行为 | 动作与前置状态、操作前后状态、可见反馈/失败记录 |
| `obstruction` | 必需文案无法理解，或必需操作因遮挡/裁切/溢出不可见、不可点或无法完成 | 仅 bbox 相交；轻微 Logo/文字位置偏差但内容与操作仍可用 | 未标注原图、required state/region；影响操作时附交互结果。bbox 只触发检查，不直接定 fail |
| `fabrication` | 无来源内容被表述为事实，且实质改变页面含义 | 合理的视觉推断、无害装饰细节、被明确保留为推断的内容 | 来源事实/未知项、候选断言/行为、语义影响说明 |
| `external_writes` | 页面造成契约不允许的外部状态变更、提交、消息或远端 mutation | 仅加载只读资源，不能单独证明发生写入 | 触发动作、请求或外部状态变化证据、允许副作用边界 |

### 红线严重度与判定算法

严重度衡量缺陷对任务/含义的影响；适用性回答该条件是否属于 case；证据置信度回答是否有足够依据。三者不可互相替代。按顺序判定：

1. **适用性：** 由冻结契约确定。无该要求则 `not_applicable`；case 记录不足以判断适用性则 `unknown`，不得默认通过。
2. **证据：** 每个状态需覆盖其契约要求；截图用于视觉判断，交互需操作前后证据，外部写入需请求或状态变化证据。证据缺失时状态为 `unknown`。
3. **影响类别：** 选择一个主要、可观察影响：`none`、`minor_degradation`、`required_state_unreachable`、`key_content_unavailable`、`core_action_unavailable`、`material_fact_misrepresented`、`primary_task_unavailable`、`core_meaning_misrepresented` 或 `external_write`。同时记录受影响的 `states` 与 `regions`。
4. **严重度映射：** S0=`none`；S1=`minor_degradation`；S2=`required_state_unreachable` / `key_content_unavailable` / `core_action_unavailable` / `material_fact_misrepresented`；S3=`primary_task_unavailable` / `core_meaning_misrepresented` / `external_write`。影响类别与严重度由 grader 校验，不允许任意组合。
5. **红线状态：** applicable 且 S0/S1 → `pass`；applicable 且 S2/S3 → `fail`；证据不足 → `unknown`；不适用 → `not_applicable`。当前结果门槛中，任一 `fail` 会使该 case E2E 失败；总分不能抵消红线失败。

| 严重度 | UI 影响锚点 | 红线结果 |
| --- | --- | --- |
| S0 无缺陷 | 冻结要求得到满足，没有可观察损失 | `pass` |
| S1 轻微 | 局部视觉/状态质量下降，但用户仍能看到、理解并完成要求；例如文字仍存在且可理解的轻微 Logo 偏位 | `pass`；在 layout/style 分数或残差记录 |
| S2 重大 | 必需内容不可理解、必需状态不可到达、核心操作不可用，或重要事实被实质误述；影响范围限于契约标明的状态/区域，但要求已受损 | `fail` |
| S3 严重 | 主要任务不可完成、页面核心含义被根本改变，或发生未授权外部写入 | `fail`；记录所有受影响状态/区域与副作用 |

严重度从**任务后果**判断，并记录覆盖范围和可恢复性：缺陷在哪些必需视口/状态出现、影响哪些契约区域、是否有契约允许的正常替代路径。单一视口不自动降级；边界框相交不自动升级。可恢复性用于说明影响，不能把契约要求的失败改判通过。证据置信度低时应标 `unknown`，不能把严重度降为 S1。

**UIR-0007 校准样例：** `desktop-settings` 中 Logo 靠近 hero 首词。人工审阅判定“We”存在、Logo 可稍向左移、无需修复，因此影响为 `minor_degradation`、严重度 S1、`obstruction` 通过；原始 Judge fail 保留在独立记录中。此样例只校准本案该状态，不外推为所有文字遮挡均轻微。

**实现状态：** `evals/pipeline/grader.mjs` 强制六个稳定 ID、适用性/状态/严重度/影响之间的一致性、影响类别与红线的对应关系，以及受影响状态/区域和证据引用。`E2ERedlineAssessment/v1` 定义单条结果；`RedlineProfile/v1` 定义 case 专属适用范围、状态/区域/obligation、触发与不触发例子、证据要求和理由。Rubric v1.1-draft 要求冻结契约包含完整 profile。grader 可校验结构和逻辑一致性，不能替代视觉事实判断。UIR-0007 是 v1.0 历史 run，不回填 profile 或重评分。旧结果缺少严重度字段时只按历史记录读取，不回填推断值、不静默重评分。

### 组级通过线

- Go：S3 红线为 0；S2 红线满足确认后的失败率门槛且不集中于关键流程；加权总分 ≥75/100；每个适用维度均达到通过线；与基线相比没有经确认的关键维度退化。
- 有条件 Go：红线满足；总分 70–74，或仅一个非关键维度略低于通过线；必须指定修复目标、负责人和复测条件。
- No-Go：任一 S3 红线、S2 红线超过确认门槛、总分 <70，或关键维度未过线且没有可接受的限制范围。

这些是首轮候选阈值。没有历史 run，不能称其为统计学上已验证的 pass line；先用开发集校准评分者和 rubric，再在封存集确认阈值。

## 评测集

| 项 | 提案 |
| --- | --- |
| 来源 | 项目维护者有权使用的公开网页截图/录屏、可复现本地页面或专门制作的合成页面任务；每条必须有来源和授权/许可说明 |
| 规模 | 开发/校准集 8 个 case；封存确认集 24 个 case。首轮可先用 8 个开发集发现 rubric 缺口；不能据此宣称方案优胜 |
| 分层 | 每组各 6 个：布局/内容简单、信息密集型、交互状态丰富、参考不完整或存在素材缺失。每层包含不同页面结构；难度以冻结的 case 特征表描述 |
| 覆盖 | 只覆盖页面还原；至少记录输入类型、页面复杂度、关键区域数、关键交互数、视口、素材可用性和可核实事实项。确认集应有素材/动态场景丰富的 case，以检出占位和静态替代 |
| 版本 | `cases.yaml` 使用独立 case ID 和 dataset 版本；每轮报告记录 git commit、case 清单版本、fixture SHA-256、参考图 SHA-256 |
| Ground truth | 固定输入 + 参考截图/页面 + 人工标注的关键区域、内容事实、交互行为、允许推断和禁止臆造项；不要求像素级源码真值 |
| 污染控制 | 开发集可见，封存集访问受限；不要把封存 prompt/截图放进系统提示、示例或评分器 few-shot；用哈希冻结资产；公开案例需记录模型可能见过原站的风险；每次更换封存 case 版本并记录原因 |
| 规模限制 | 24 个确认 case 适合发现明显差异，不保证检出小效应；若置信区间跨越决策阈值或分层结果方向冲突，结论为不确定并扩样，不强行排名 |

禁止把真实用户生成的页面/素材直接提交进仓库。仓库 fixture 仅保存许可明确、去除个人信息且体量可控的素材；其他输入用本地受限路径或可复现获取说明。

## 评分器、校准与偏差检查

| 类型 | 用途 | 校准/报告要求 |
| --- | --- | --- |
| 确定性检查器 | 项目目录与入口/启动命令、依赖安装或静态打开、浏览器加载、资源失败、控制台错误、目标视口截图、溢出、指定交互动作结果 | 记录检查器版本、失败日志；不把“可加载”当作视觉质量 |
| LLM Judge | 对照输入、固定参考、事实标注表及 Rubrics，对视觉/内容/证据维度给 0–4 分和证据位置 | 对开发集双盲评分；报告与人工裁决的 quadratic weighted Cohen’s κ，目标 κ≥0.60；分歧 >1 级的比例 ≤10% |
| 人工评审 | 视觉质量最终裁决、歧义 case、评分器校准与争议样本 | 至少两名评审独立评校准子集；报告 κ；分歧由第三次裁决或共识记录解决 |

首轮校准建议：从开发集抽取至少 8 个输出，覆盖每个实验组；两名人工评审 + Judge 独立评分。少于 30 个成对判断时 κ 仅作方向性指标，必须同时报告原始一致率、混淆矩阵和样本数；不得声称达到稳健校准。κ<0.60 时先修订 Rubrics / Judge 输入并重测，不进入确认集结论。

每轮偏差测试至少检查：

- 盲化组名、随机化呈现顺序，避免 Judge 知道方案身份；对同一输出改变展示位置后评分差绝对值应 ≤0.25/4。
- 成对比较交换 A/B 顺序后，偏好翻转率 ≤10%；超出则改为单项独立评分或人工裁决。
- 检查长代码/长解释、框架标记、品牌熟悉度、页面风格、截图顺序是否系统性影响评分；相同截图与相同参考不应因组名而改变评分。
- 报告各组 Judge 与人工的平均差、按维度差异，以及高低复杂度 case 的偏差；任何组间差异 >0.25/4 需审查评分器是否偏袒某种输出形态。

以上 κ 和偏差阈值是预先建议的验收标准，实际校准结果在第一轮完成前均记为“未测”。

## 统计比较

- 同一 case 在各组配对；每个组至少一次运行。若后续多次采样，先在 case×组内求均值，再按 case 做配对差异，避免把重复采样误当独立样本。
- 报告每维度及总分的组均值、相对基线差、case 数、标准差和 95% bootstrap 区间；以 case 为重采样单位，分层抽样并固定随机种子。
- 同时报告通过率/红线率和分层结果。样本太少或区间跨 0 时，标注证据不足，不把点估计差异写成胜负。
- 错误分类先用固定 taxonomy 多标签标注，再报告出现该错误的 case 数 / 有效 case 数；错误类型可重叠，比例总和可能超过 100%。

## 运行设置与资源

本版本按要求暂不设定试验次数、温度、单次超时、重试和成本上限。执行前必须把这些值写入 run manifest；没有 manifest 的结果仅作试运行，不进入版本 Go/No-Go 决策。

## 产出与时间

- 每个 run：manifest、逐 case 产物位置与校验和、自动检查 JSON、Judge 原始评分、人工评分、聚合报告。
- 报告包含报告日期、case/dataset 版本、被测 Skill commit、模型/effort、客户端与浏览器版本、评测负责人、决策会议日期。
- 决策会议时间待项目负责人安排；不在文档中虚构日期。

## 已知局限

1. 这是单一模型、单一 restore 工作流的离线比较，结论不能外推到其他模型、其他模式或线上用户体验。
2. 当前对照设计按递进方案组织，无法拆开 Harness 与附加能力的交互效应。
3. LLM Judge 对图像、品牌和风格可能存在偏好；需要盲评、人工校准和偏差测试，不能把 Judge 分数当客观真值。
4. 没有 trace 时只评最终产物和可观察交互，无法归因中间步骤、工具选择或 brief 到项目实现的传递损失。
5. 参考图并非完整真值；不可见交互与缺失素材必须通过标注限定推断边界。
6. 不同方案可能交付静态文件或需构建的项目；评测运行需预先固定启动适配器、网络/依赖策略与浏览器环境。文件数和框架选择不作为质量分，但启动失败计入红线。
7. 自动化模型调用 Harness/Plugin/Skill 的接入方式尚未核实；管线可先自动处理已收集产物的渲染、检查、评分和汇总，端到端发起各组生成任务需适配当前客户端/接口。
