# URL → observed restoration task

You receive only a target website URL. During the Harbor prepare step, observe the rendered site and infer a concrete restoration task. Use the injected Restore Skill, existing contract fields and Loop Criteria. Do not ask the user to write a brief or choose the site's purpose when the page provides enough evidence.

Start with the provided browser tool rather than writing or installing another adapter: `node <SKILL_DIR>/scripts/restore/observe-url.mjs TARGET_URL /home/pwuser/restore-run`. Playwright Core 1.58.0 is bundled under `<SKILL_DIR>/tools/browser/node_modules/playwright-core`; browser binaries are in /ms-playwright. Inspect observation.json and its screenshots. The helper records desktop/mobile top, middle, footer and a scroll sequence using rendered DOM and media response metadata, without reading application source. Supplement it only for evidenced gaps.

The helper also creates the draft contract.json with the existing schema, observed environment, visual evidence hashes and initial states. Complete that same contract's task_description, journey states and C1/C2/C3 obligations; do not reconstruct the schema from memory or create another task artifact. Seal the observed scope before attempting optional supplemental probes. Missing deep coverage must be explicit in unknowns rather than consuming the entire step and losing all task output.

1. Open the URL. Confirm the observed URL and page identity. Observe the first screen, meaningful middle sections, footer, desktop/mobile viewports, and the core visible interaction. For motion, capture a short input/response sequence. Follow visible links only as needed to understand the core scenario within the permitted hosts and budget. If a required page/resource is inaccessible, record the exact limitation in contract.unknowns.
2. Infer the design scenario: page type, intended audience, principal user goal, content hierarchy, visual language and interaction path. Treat audience/business intent as inference unless explicitly stated on the page. Never invent hidden APIs, transactions, business facts, or unseen states.
3. Write ONLY contract.json.task_description for the narrative task:
   - title: short task name in the reference site's language.
   - scenario: describe the observed design scenario, not its source implementation.
   - user_intent: null when unknown; otherwise {text, basis: "observed"|"inferred"}. Inferred intent guides the explanation, never adds implementation requirements.
   - description: a self-contained implementable restoration instruction. Explain what to reproduce, the core user journey and salient visual/motion features, with explicit observation boundaries. Reference declared states/obligations rather than duplicating their exact tables. No framework attribution, source excerpts or evaluator answers.
   - evidence_refs: IDs of the frozen screenshots/sequences supporting this description.
4. Put executable facts in their existing fields once: states = viewports/actions/reachable states; obligations = visual/behavior requirements and acceptance; resources = allowed assets; unknowns = evidence gaps. Do not create task-description.json, task.md or a second independently authored design brief. Do not shrink a scroll narrative to its hero simply because later states take time to capture.
5. Before the deadline run `node <SKILL_DIR>/scripts/restore/seal-prepare.mjs /home/pwuser/restore-run`. It validates the full existing restore/v0.2 contract and task_description, locks its hash, projects generation-input.json and design_brief.md, and writes evaluations/prepare.json. Fix any validation error using the same observed evidence; do not invent a different contract schema. This is a domain I/O helper, not a second lifecycle. Reserve the final 60 seconds for sealing. If evidence is insufficient, finish with incomplete/blocked and explain it rather than fabricating a task.

Default clean-room policy: inspect rendered DOM text, geometry, screenshots and observed asset URLs; do not read application source, source maps or implementation bundles. Source-assisted inspection is available only when the frozen source policy explicitly allows it. Independent assessment is separate from the generated task description.
